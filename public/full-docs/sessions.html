Sessions

Use sessions to coordinate checkout

Sessions connect your backend, the Flywire Checkout UI, and follow-up status. Use authenticated sessions for production integrations and session runs for each checkout attempt.

Review API guide See events

Integration flow

  1. 1Create or resume
    Your backend creates a session or resumes one that can continue.
  2. 2Start a run
    The browser starts checkout with the returned session run values.
  3. 3Follow up
    Your backend checks session state or receives configured events.
Recommended path:

Use authenticated sessions whenever your integration has a backend. They keep API credentials server-side, support status lookup and events, and make it easier to resume or continue a payer's transaction.

Session model

Sessions and session runs

A session is the backend record that represents the checkout transaction your integration wants Flywire Checkout to coordinate. It can be queried and monitored until it is archived.

A session run is one pass through the Flywire Checkout UI. A session can contain one or more runs, which lets a payer return to checkout without creating a duplicate payment attempt for the same business transaction.

Session

Created or resumed by your backend through the public API. It groups the transaction configuration, follow-up state, and related runs.

Session run

Returned with a run identifier and token. Your frontend passes these values to the checkout runtime to start or continue the UI.

Events

Describe selected payer actions and system behavior. Configure an eventUrl when your backend should receive notifications.

Recommended lifecycle

Authenticated sessions

Authenticated sessions are the production default for most client integrations. Your backend uses Public API credentials to create or resume the session, then returns only browser-safe values to your frontend.

  1. Your backend calls POST YOUR_PUBLIC_API_BASE_URL/commercial-payex/v2/session to create a session, or POST YOUR_PUBLIC_API_BASE_URL/commercial-payex/v2/session/SESSION_ID to resume one.
  2. The API response includes a SESSION_ID, SESSION_RUN_ID, and SESSION_RUN_TOKEN.
  3. Your frontend loads connect.js and starts checkout with those session run values.
  4. Flywire Checkout validates the session and run before showing the checkout UI.
  5. The frontend on_end callback reports completed or canceled for the browser experience.
  6. Your backend follows up by querying session state and/or handling configured event notifications.

This approach gives you stronger security, backend observability, support for one session with multiple runs, fewer duplicate payments, and a path to resume or continue a transaction.

Lightweight fallback

Anonymous sessions

Anonymous sessions are intended for clients without a backend that need a lightweight, one-off checkout operation. They are simpler to start, but they provide less control and are not the recommended path for production integrations that can use a backend.

Best fit

Frontend-only use cases where the operation is simple and the client accepts a reduced follow-up model.

Trade-offs

Less secure than authenticated sessions, not all flows are supported, and the response comes directly from the UI.

Run behavior

Anonymous sessions always have exactly one session run and cannot be reused after completion.

Recovery guidance

Expiry and reuse

Session runs are time-limited. Create or resume a run close to the moment the payer is ready to start checkout, and be prepared to recover if the run expires before checkout finishes.

  • If the payer is returning to the same unfinished transaction, resume the existing session from your backend and send the fresh run values to the browser.
  • If the transaction should start over, create a new session and discard the expired browser values.
  • Do not keep retrying old SESSION_RUN_TOKEN values in the browser. Ask your backend for current session run details.
Backend confirmation

Status follow-up

on_end is a frontend callback that helps your page react when the checkout UI closes. It should not be the only signal used for payment, order, or fulfillment decisions.

For operational follow-up, use backend session lookup with GET YOUR_PUBLIC_API_BASE_URL/commercial-payex/v2/session/SESSION_ID and/or server event notifications configured with config.eventUrl. This keeps status decisions on your backend and makes your integration more resilient to browser closes, network changes, and delayed payment updates.
