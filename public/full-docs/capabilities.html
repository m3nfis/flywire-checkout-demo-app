Capabilities

Checkout capabilities at a glance

Flywire Checkout V2 supports payment collection, payment method tokenization, embedded checkout, localization, offer controls, and backend-visible session follow-up.

Use capabilities with sessions:

Most production integrations should create or resume a session on the backend, pass the session run values to the browser, and start checkout with window.cpxCore.start(cpxInitFields). See the integration guide and init fields reference for complete startup examples.

Core checkout modes

Transaction modes

Choose the transaction mode that matches the business outcome you want checkout to produce. Each mode uses the same startup method and session pattern, but the transaction.type and transaction.details fields differ.

Payment

Collect a payment for a known amount. Use transaction.type: "payment" with details.amount.

Tokenization

Store a payer payment method for later use. Use transaction.type: "tokenization"; amount is optional when details are included.

Optional tokenization

Collect a payment and allow the payer to save the method when supported. Use transaction.type: "optionalTokenization" with an amount.

Implicit tokenization

Collect a payment while creating a reusable method as part of the checkout flow where supported. Use transaction.type: "implicitTokenization" with an amount.

Preauthorization

Authorize funds without immediate capture by adding authorization: "preauth" in transaction details where the flow supports it.

Session-backed checkout

Coordinate the frontend flow with backend status, event delivery, and recovery by passing session.id, session.runId, and session.runToken.

window.cpxCore.start({
  recipient: {
    clientId: "YOUR_CLIENT_ID",
    code: "YOUR_RECIPIENT_CODE"
  },
  transaction: {
    type: "optionalTokenization",
    details: {
      amount: "123.45"
    }
  },
  session: {
    id: "SESSION_ID",
    runId: "SESSION_RUN_ID",
    runToken: "SESSION_RUN_TOKEN"
  },
  response: {
    onEnd: function (reason, payload) {
      console.log("Checkout ended:", reason, payload);
    },
    onError: function (type, payload) {
      console.error("Checkout error:", type, payload);
    }
  }
});
Presentation mode

Embedded checkout

Use embedded checkout when the Flywire Checkout UI should appear inside a page area you control instead of opening in the standard runtime experience. Provide config.embedTo with a CSS selector for an existing container.

<div id="cpx-checkout"></div>

<script>
  window.cpxCore.start({
    recipient: {
      clientId: "YOUR_CLIENT_ID",
      code: "YOUR_RECIPIENT_CODE"
    },
    transaction: {
      type: "payment",
      details: {
        amount: "123.45"
      }
    },
    session: {
      id: "SESSION_ID",
      runId: "SESSION_RUN_ID",
      runToken: "SESSION_RUN_TOKEN"
    },
    config: {
      embedTo: "#cpx-checkout"
    },
    response: {
      onEnd: function (reason, payload) {
        console.log("Checkout ended:", reason, payload);
      }
    }
  });
</script>

For a step-by-step embedded example, see embedded checkout in the integration guide.

Authorize before capture

Preauthorization

Add authorization: "preauth" in transaction.details when your integration needs to authorize funds before capture and the selected payment method supports that behavior.

transaction: {
  type: "payment",
  details: {
    amount: "123.45",
    authorization: "preauth"
  }
}

Capture and authorization-management calls are backend operations. See the API guide for related payment operation examples.

Offer filtering and sorting

Offer rules

Offer rules let your integration influence which payment offers are displayed and how they are ordered. Common filters include payment method, currency relationship, and advanced filters such as isNotAmex.

config: {
  offerRules: {
    filters: {
      method: ["credit_card", "bank_transfer"],
      currency: ["payerCurrency", "recipientCurrency"],
      advanced: ["isNotAmex"]
    },
    sort: [
      {
        field: "method",
        order: ["bank_transfer", "credit_card"]
      }
    ]
  }
}

Use offer rules to align checkout choices with your integration policy while still allowing Flywire Checkout to present eligible payment options for the payer and transaction context.

Locale and form behavior

Localization and configurable forms

Set config.locale to request a supported checkout locale, such as en, en-US, es, fr-FR, de-DE, pt-PT, it-IT, ko-KR, zh-CN, ja-JP, id-ID, or vi-VN.

Use showPayerForm, showRecipientForm, and disabledFields to control which payer or recipient fields Flywire Checkout should collect or lock in the UI. You can prefill payer fields such as name, email, phone, and address through payer.fields.

payer: {
  fields: {
    firstName: "PAYER_FIRST_NAME",
    lastName: "PAYER_LAST_NAME",
    email: "payer@example.com",
    country: "US"
  }
},
config: {
  locale: "en-US",
  showPayerForm: "auto",
  showRecipientForm: false,
  disabledFields: ["payer.email"]
}
Client-visible pricing context

Fee and rate visibility

Depending on the selected offer and transaction context, checkout may show payer-facing fee and rate information such as Flywire conversion fee, service fee, surcharge, exchange rate, and markup rate.

Keep your own UI language high-level unless Flywire provides integration-specific pricing guidance. The checkout offer presentation is the best source for payer-facing amounts and rate details at the moment of payment.

Operational status

Events and session visibility

The frontend response.onEnd callback tells your page that the checkout UI ended with completed or canceled. It should not be the only source of payment truth for fulfillment, order state, or reconciliation.

For operational decisions, use backend session lookup and/or server event notifications. See status follow-up, the callbacks versus events guidance, and the get session info example.
