Integration guide

Start checkout with an authenticated session

Use your backend to create or resume a Flywire Checkout V2 session, pass the session run values to your web app, then start checkout with window.cpxCore.start.

Understand sessions View field reference

Integration flow

  1. 1Backend creates session
    Use server-side credentials and send safe identifiers to the browser.
  2. 2Browser starts checkout
    Load the connector and start checkout with session context.
  3. 3Backend confirms status
    Use events or session state for operational decisions.
Keep secrets on your backend:

The browser should receive only the session values needed to start checkout. API credentials, session creation, resume logic, and final status checks belong on your server.

Before you start

Prerequisites

Flywire provides two environments. Use the correct origin for both the gateway script (browser) and the public API (backend):

Environment Gateway origin (browser) Public API base (backend)
Demo https://checkout.demo.flywire.com https://checkout.demo.flywire.com/public-api-demo
Production https://checkout.flywire.com https://checkout.flywire.com/public-api

Load the browser runtime from the gateway origin:

  • Demo: https://checkout.demo.flywire.com/gateway/connect.js
  • Production: https://checkout.flywire.com/gateway/connect.js

You also need:

  • YOUR_CLIENT_ID and YOUR_RECIPIENT_CODE — provided by Flywire for your recipient.
  • YOUR_PUBLIC_API_KEY — secret key for backend session calls (never expose in the browser).
  • A page in your web app where checkout starts after your backend returns SESSION_ID, SESSION_RUN_ID, and SESSION_RUN_TOKEN.
  • Optionally, an event receiver such as https://example.com/cpx-events for backend notifications.

Authenticated sessions are the recommended integration path. Anonymous sessions can be useful for lighter setups without a backend, but they provide less control over credentials, recovery, and payment follow-up.

Step 1

Create or resume a session on your backend

Your backend creates a new Flywire Checkout V2 session, or resumes an existing one when the payer is returning to an unfinished checkout. The response should be reduced to the safe values your browser needs.

async function createCpxSession() {
  const response = await fetch("YOUR_PUBLIC_API_BASE_URL/commercial-payex/v2/session", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-Authentication-Key": "YOUR_PUBLIC_API_KEY"
    },
    body: JSON.stringify({
      config: {
        eventUrl: "https://example.com/cpx-events"
      }
    })
  });

  if (!response.ok) {
    throw new Error("Unable to create Flywire Checkout V2 session");
  }

  const session = await response.json();

  return {
    id: session.id,
    runId: session.runId,
    runToken: session.runToken
  };
}

When a payer returns to an existing session, resume it from your backend and return a fresh set of browser-safe run fields to the frontend.

async function resumeCpxSession() {
  const response = await fetch("YOUR_PUBLIC_API_BASE_URL/commercial-payex/v2/session/SESSION_ID", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-Authentication-Key": "YOUR_PUBLIC_API_KEY"
    }
  });

  if (!response.ok) {
    throw new Error("Unable to resume Flywire Checkout V2 session");
  }

  const data = await response.json();

  return {
    id: data.id,
    runId: data.runId,
    runToken: data.runToken
  };
}

Send those values to the browser as SESSION_ID, SESSION_RUN_ID, and SESSION_RUN_TOKEN, then use the same checkout startup call below.

For resume and lookup patterns, see sessions and the API guide.

Step 2

Load connect.js

Load the frontend runtime from the gateway origin matching your environment before calling window.cpxCore.start. Add the script on the page that launches checkout, or load it through your application shell if checkout is available across several routes.

<script src="https://checkout.demo.flywire.com/gateway/connect.js" defer></script>
<script src="https://checkout.flywire.com/gateway/connect.js" defer></script>

Before starting checkout, make sure the script has loaded and window.cpxCore is available.

Step 3

Start checkout

After your backend returns the session run values, pass them into window.cpxCore.start(cpxInitFields) together with the recipient, transaction, and response callbacks.

window.cpxCore.start({
  recipient: {
    clientId: "YOUR_CLIENT_ID",
    code: "YOUR_RECIPIENT_CODE"
  },
  transaction: {
    type: "payment",
    details: {
      amount: "123.45"
    }
  },
  session: {
    id: "SESSION_ID",
    runId: "SESSION_RUN_ID",
    runToken: "SESSION_RUN_TOKEN"
  },
  response: {
    onEnd: function (reason, payload) {
      console.log("Checkout ended:", reason, payload);
    },
    onError: function (type, payload) {
      console.error("Checkout error:", type, payload);
    }
  }
});

Payment is shown here as the minimum practical example. Tokenization and other checkout capabilities use the same startup pattern with different transaction values; see capabilities and reference.

Step 4

Handle onEnd and onError

onEnd reports that the checkout UI completed or was canceled. Do not treat it as the only source of payment truth. Use backend session status, events, or API lookups before updating orders, balances, or fulfillment.

function startCheckout(session) {
  window.cpxCore.start({
    recipient: {
      clientId: "YOUR_CLIENT_ID",
      code: "YOUR_RECIPIENT_CODE"
    },
    transaction: {
      type: "payment",
      details: {
        amount: "123.45"
      }
    },
    session: {
      id: session.id,
      runId: session.runId,
      runToken: session.runToken
    },
    response: {
      onEnd: async function (reason, payload) {
        showCheckoutClosedMessage(reason);
        await refreshSessionStatusFromYourBackend(session.id);
      },
      onError: function (type, payload) {
        showRecoverableCheckoutError(type, payload);
      }
    }
  });
}

If you configure eventUrl when creating the session, your backend can also receive event notifications. The events guide covers that flow in more detail.

Step 5

Use embedded checkout when needed

By default, checkout opens in the standard runtime experience. To embed checkout into a specific page container, include config.embedTo with a CSS selector that points to an existing element.

<div id="cpx-checkout"></div>

<script>
  window.cpxCore.start({
    recipient: {
      clientId: "YOUR_CLIENT_ID",
      code: "YOUR_RECIPIENT_CODE"
    },
    transaction: {
      type: "payment",
      details: {
        amount: "123.45"
      }
    },
    session: {
      id: "SESSION_ID",
      runId: "SESSION_RUN_ID",
      runToken: "SESSION_RUN_TOKEN"
    },
    config: {
      embedTo: "#cpx-checkout"
    },
    response: {
      onEnd: function (reason, payload) {
        console.log("Checkout ended:", reason, payload);
      },
      onError: function (type, payload) {
        console.error("Checkout error:", type, payload);
      }
    }
  });
</script>
Step 6

Test checklist and common mistakes

  • Confirm connect.js loads from the correct environment (checkout.demo.flywire.com or checkout.flywire.com) before checkout starts.
  • Use runToken in the browser session object, not a different field name.
  • Keep YOUR_PUBLIC_API_KEY on the backend and never place it in browser code.
  • Make sure YOUR_CLIENT_ID and YOUR_RECIPIENT_CODE match the recipient you expect to use.
  • Handle both completed and canceled reasons from onEnd as UI outcomes.
  • Use session status, configured events, or API lookups before making final business decisions.
  • If using embedded checkout, verify the config.embedTo selector exists before calling window.cpxCore.start.
