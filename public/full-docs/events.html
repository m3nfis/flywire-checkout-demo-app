Events

Handle backend event notifications

Use backend event notifications when your server should receive selected Flywire Checkout session, payment, session-run, and reconcile updates independently from the browser callback.

Review sessions Open API guide

Integration flow

  1. 1Set eventUrl
    Include your HTTPS receiver when creating the session.
  2. 2Receive JSON
    Flywire posts one event object per notification.
  3. 3Verify and process
    Check the digest when present, respond quickly, and process safely.
Backend signal:

Events are server-to-server notifications. They complement frontend onEnd callbacks, but they are configured and handled by your backend.

Notification endpoint

When to use eventUrl

Configure eventUrl when your backend needs server notifications for selected client-relevant Flywire Checkout activity. This is useful for reconciliation, operational monitoring, and payment/session follow-up that should not depend on the payer's browser staying open.

If config.eventUrl is omitted or empty when the session is created, Flywire Checkout does not send client server event notifications for that session.

Create-session config

Enable events for a session

Include your HTTPS receiver in the create-session request. You can also include metadata that helps your backend associate later events with your own order, cart, or account records.

{
  "config": {
    "eventUrl": "https://example.com/cpx-events"
  }
}

Keep metadata client-safe and avoid storing sensitive data in fields that may appear in logs or operational tooling.

Webhook payload

Expected webhook shape

Each notification sends a single JSON object to your event receiver. Event payloads use snake_case fields such as event_type, event_resource, event_date, session_id, and session_run_id. Not every internal Flywire Checkout event is forwarded; expect a selected set of client-relevant categories such as payment, session, session-run, and reconcile activity.

{
  "event_type": "payment.updated",
  "event_resource": "payment",
  "event_date": "2026-05-08T09:00:00Z",
  "session_id": "SESSION_ID",
  "session_run_id": "SESSION_RUN_ID",
  "payment": {
    "payment_id": "PAYMENT_ID"
  }
}

The exact fields can vary by event type and resource. Store the raw payload for troubleshooting, but build your business handling around the documented snake_case fields your integration needs.

Digest header

Verify the HMAC digest

When a shared secret is available for the recipient associated with the session, Flywire adds X-Flywire-Digest: <base64-hmac>. The value is computed from the UTF-8 JSON request body and the recipient shared secret using HMAC-SHA256.

If no shared secret is configured, the digest header is omitted. When the header is present, verify it before trusting the payload. Load YOUR_SHARED_SECRET from backend secret storage and never send it to browser code.

import crypto from "node:crypto";

function verifyCpxDigest(rawJsonBody, receivedDigest) {
  if (!receivedDigest) {
    return false;
  }

  const expectedDigest = crypto
    .createHmac("sha256", "YOUR_SHARED_SECRET")
    .update(rawJsonBody, "utf8")
    .digest("base64");

  const received = Buffer.from(receivedDigest);
  const expected = Buffer.from(expectedDigest);

  return received.length === expected.length && crypto.timingSafeEqual(received, expected);
}

Use the raw request body exactly as received. Parsing and re-stringifying JSON can change whitespace or key order and produce a different digest.

Receiver behavior

Delivery handling advice

  • Return a 2xx response quickly after validating and storing the notification.
  • Process events idempotently. The same event may be delivered more than once, and retry-safe handling should produce the same final result.
  • Log the event type, event resource, session id, session run id, and payment id when present.
  • Move slow business work to an internal queue or background worker instead of making Flywire wait for downstream systems.
  • Use backend session lookup when you need the latest session state before making an irreversible business decision.
Browser signal versus final state

Callbacks vs events

onEnd is a frontend callback from the checkout UI. It tells your page that the user flow ended with completed or canceled, which is useful for navigation and messaging.

eventUrl notifications are backend messages. Use them, together with session lookup, for operational follow-up such as payment status tracking, reconciliation, and fulfillment decisions.

Practical rule:

Let onEnd update the browser experience. Let your backend confirm status through events, API lookups, or both.
